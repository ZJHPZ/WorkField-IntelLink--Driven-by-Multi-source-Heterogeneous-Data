# 智能体微服务模板设计文档 · 「苏格拉底对话」模式

> 版本: v1.0
> 日期: 2026-08-19
> 状态: 落地设计稿(基于已落地实现拆解)
> 原型位置: `参考/苏格拉底对话/`(数知项目已上线)
> 定位: **可复用模板** —— 后续在本项目开发同类"人格微服务"组件时,以此文档为参照
> 核心思想: **人格即服务(Persona-as-a-Service)**

---

## 1. 设计定位与总体思路

### 1.1 这个微服务解决什么问题

大模型对话能力需要与具体业务解耦。与其在每个业务项目里各自封装一次星火调用、各自写一套流式转发、各自维护一份人设 prompt,不如把"**一个人格 + 一次流式对话**"做成一个独立微服务,按需复用。

「苏格拉底对话」是这一模式的落地产物:它把"苏格拉底式导师"这个**人格**和"引导反思"这个**业务**打包成一个独立 FastAPI 微服务,数知项目通过 HTTP 调用它完成学习反思功能。**它不依赖数知,数知也不依赖它**——两者只通过一组 HTTP 契约相连。

### 1.2 核心设计思想:人格即服务

```
任意人格 = 一段 system prompt 文本
任何业务 = 拼一段 user prompt
输出     = 统一的 SSE 流
```

- **人格是常量,不是逻辑**:苏格拉底的人格就是 `services/socratic_prompt.py` 里的一个 `SYSTEM_PROMPT` 字符串常量。改人格 = 改文本,不改代码结构。
- **业务是拼装,不是编程**:每次请求只需把用户输入 + 可变参数(如 `user_level`)拼成一段 user prompt,其余全交给模型。
- **交互是协议,不是耦合**:微服务只对外输出 SSE 事件流,消费方(前端/其他服务)按协议解析即可,双方零代码依赖。

> 由此推导出本模式的扩展力:`/api/socratic/generate-simple` 端点接受**任意** `system_prompt`,说明"人格微服务"可以完全通用化——**想加一个新人格,加一个 prompt 文件即可,基础设施一行不用改**。

### 1.3 设计原则

| # | 原则 | 在苏格拉底中的体现 |
|---|---|---|
| 1 | **人格与引擎分离** | `socratic_prompt.py`(人格)与 `spark_service.py`(引擎)是两个文件,引擎完全人格无关 |
| 2 | **真流式,不模拟** | `httpx.AsyncClient.stream` 直连星火,一帧帧转发;绝不 sleep 伪造 |
| 3 | **无状态服务** | 不引数据库、不做会话存储;可变状态(用户水平等)全部由调用方传参 |
| 4 | **密钥走配置** | API key 只存 `.env`,经 `pydantic-settings` 注入,代码零密钥 |
| 5 | **契约先行** | SSE 事件格式是唯一契约,前后端各自实现、互不依赖 |
| 6 | **渐进式结构化** | 流式输出携带 `section` 标记,前端边收边分类,不必等全文结束 |

## 2. 总体架构

### 2.1 目录结构与分层

```
苏格拉底对话/
├── main.py                    # 应用入口(路由挂载 + CORS + uvicorn)
├── core/
│   └── config.py              # 配置层(pydantic-settings 读 .env)
├── api/
│   └── socratic_chat.py       # 契约层(SSE 路由 / health)
├── services/
│   ├── spark_service.py       # 引擎层(星火真流式,人格无关,可复用核心)
│   ├── socratic_prompt.py     # 人格层(SYSTEM_PROMPT + build_user_prompt)
│   └── __init__.py
├── utils/
│   └── quotes.py              # 附加物(名言库,仅供前端展示用,与核心逻辑无关)
├── requirements.txt           # 全部依赖 6 个包
└── package.json / *.cjs       # 数知侧截图测试脚本,非服务本体
```

**四层职责:**

| 层 | 文件 | 职责 | 是否人格相关 |
|---|---|---|---|
| 入口 | `main.py` | 组装应用、跨域、启动 | 否 |
| 配置 | `core/config.py` | 密钥/URL/端口/模型 | 否 |
| 契约 | `api/socratic_chat.py` | 定义 HTTP + SSE 协议 | 半(端点命名随业务) |
| 引擎 | `services/spark_service.py` | 星火流式调用的完整封装 | **否(换人格无需动)** |
| 人格 | `services/socratic_prompt.py` | 人设 + 用户消息拼装 | **是(唯一需要动的)** |

> 分层的价值:**换人格时,只有"人格层"要改**,其余四层原样复用。这正是本文档作为模板的落点。

### 2.2 请求生命周期(一次"生成"的全链路)

```
前端(shuzhi-frontend)          苏格拉底微服务 :8001              讯飞星火
        │                              │                           │
        │ POST /api/socratic/generate  │                           │
        │──{question, topic, user_level, user_id}──→│              │
        │                              │ 拼装 user prompt           │
        │                              │ (socratic_prompt.build)    │
        │                              │──POST spark(stream:true)──→│
        │                              │◄── SSE data:{json}×N ──────│
        │◄── SSE: data:{type,content,section}×N ──│                   │
        │◄── SSE: data:{done} ─────────│                           │
```

**前端消费(数知侧实现):**

```
fetch → ReadableStream → TextDecoder → 按行切分 → 解析 "data:" JSON
  → 边收边渲染(带 section 分类)→ 流结束后正则二次结构化三板块
  → AbortController 支持中途取消(新请求顶掉旧请求)
```

### 2.3 为什么 SSE 而不是 WebSocket / 普通 HTTP

| 方案 | 适用 | 弃用原因 |
|---|---|---|
| **SSE(采纳)** | 服务端 → 客户端单向流式文本 | 实现极简(纯 HTTP + 分帧),浏览器原生 fetch 即可消费,天然兼容代理 |
| WebSocket | 双向实时 | 此场景只有单向生成,WS 引入握手/心跳/断线重连复杂度,收益为零 |
| 普通 HTTP 长轮询 | 低频 | 无法逐字渲染,体验差 |

SSE 在这里被用作**通用的"模型输出管道"**:任何需要流式文本的业务(反思、问答、建议)都走同一条 `data:` 分帧通道。

## 3. 核心引擎:`spark_service.py`(可复用内核)

### 3.1 对外接口(人格无关)

```python
class SparkService:
    async def stream_chat(system_prompt: str, user_message: str)
        -> AsyncGenerator[{type: 'text'|'thinking'|'done'|'error', content: str}]
    async def generate_socratic_reflection(question, topic, user_level)  # 苏格拉底专用,组合层
    async def health_check() -> bool                                      # max_tokens=1 探活
```

`stream_chat()` 是**唯一需要理解的内核**——它把"调星火 + 解析 SSE + 归一化"完整封装:

### 3.2 请求构造

```python
# 鉴权: OpenAI 兼容, Bearer token
headers = {"Authorization": f"Bearer {api_password}", "Content-Type": "application/json"}

payload = {
    "model": "spark-x",
    "messages": [
        {"role": "system", "content": system_prompt},
        {"role": "user",   "content": user_message},
    ],
    "stream": True,
    "temperature": 0.7,
    "max_tokens": 800,
    "thinking": {"type": "disabled"},   # 关闭思维链,只输出正文
}
```

关键点:模型 `spark-x`(星火 Agent 开放平台 OpenAI 兼容接口);`thinking.disabled` 保证流式帧干净(只有 content)。

### 3.3 流式解析(三段式)

```
① 建立流:  httpx.AsyncClient(timeout=60).stream("POST", url, ...)
② 按行切:  async for line in response.aiter_lines()
③ 归一化:  每行 "data:{json}" →
               code!=0        → yield {type:"error", content:...}
               delta.reasoning_content → yield {type:"thinking", ...}   # 思维链
               delta.content          → yield {type:"text", content}    # 正文
               "[DONE]"      → yield {type:"done"}; return
```

### 3.4 错误处理(必须抄)

| 场景 | 处理 | 表现 |
|---|---|---|
| HTTP 非 200 | 读 body 截 500 字记日志 | yield `error` 事件,终止 |
| HTTP 200 但 `code!=0` | 记日志(含 code+message) | yield `error` 事件,终止 |
| 连接异常 | `httpx.HTTPError` 捕获 | yield `error` 事件 |

错误**永不抛出到路由层**——统一转成 SSE `error` 事件,前端直接展示。

## 4. 人格工程:`socratic_prompt.py`

### 4.1 结构(本模式的人格标准写法)

```python
SYSTEM_PROMPT = """...人设全文,定义角色、输出格式、核心原则..."""

def build_user_prompt(question, topic="", user_level="初级") -> str:
    level_hint = {"初级": "...", "中级": "...", "高级": "..."}
    hint = level_hint.get(user_level, level_hint["初级"])
    topic_line = f"涉及的知识领域：{topic}" if topic else ""
    return f"{hint}\n{topic_line}\n\n用户的问题：\n{question}\n\n请按照格式生成..."
```

### 4.2 设计要点(苏格拉底人格的示范)

| 要点 | 实现 | 价值 |
|---|---|---|
| **输出格式硬约束** | 人设里规定三个标记段 `【引导性问题】【关键假设检验】【一句话反思】` | 模型输出可被前端正则结构化(见 §6) |
| **分级适配** | `user_level` 映射到不同引导提示 | 同一人格按用户水平差异化输出 |
| **长度上限** | "整个反思不超过300字" | 控成本、控体验 |
| **行为边界** | "绝不直接回答知识性问题""不评价用户" | 人格有明确的"不做什么" |

> 这些是**任何新人格都应具备的骨架**:角色定义 + 输出格式约束 + 边界/禁忌 + 可参数化的分级策略。

## 5. API 契约

### 5.1 `POST /api/socratic/generate`(领域端点)

```json
{
  "question": "什么是MapReduce？",
  "topic": "大数据",
  "user_level": "初级",
  "user_id": "user_123"
}
```

**SSE 响应**(`data:{json}\n\n` 分隔,`[DONE]` 结束):

```
data: {"type":"text","content":"① 你每天点外卖时...","section":"questions"}
data: {"type":"text","content":"\n\n【关键假设检验】\n你假设...","section":"assumptions"}
data: {"type":"done","content":"","section":"reflection"}
data: [DONE]
```

`section` 在前端动态归类,事件流推进时 `current_section` 随标记出现而升级(反向优先匹配:一句话反思 > 关键假设检验 > 引导性问题)。

### 5.2 `POST /api/socratic/generate-simple`(通用端点 —— 模板价值的证明)

```json
{
  "system_prompt": "你是XXX人设...",
  "user_message": "用户的话...",
  "temperature": 0.7,
  "max_tokens": 800
}
```

不带任何苏格拉底格式约束,`system_prompt` 直接透传星火。**它说明:基础设施已完全通用,新增人格零成本。**

### 5.3 `GET /api/socratic/health`

```json
{ "status": "ok" | "degraded", "model": "spark-x" }
```

探活方式:`max_tokens=1` 的最小请求,HTTP < 500 即存活。

### 5.4 SSE 帧格式速查

| type | 字段 | 含义 |
|---|---|---|
| `text` | `content`, `section` | 正文增量,section 当前板块 |
| `done` | `content`(可选) | 流结束 |
| `error` | `content` | 错误信息(前端前缀 ❌) |

## 6. 前端接入模式(数知侧参考实现)

### 6.1 网络层 `api/socratic.ts`

- `VITE_SOCRATIC_API_URL` 环境变量决定直连地址(开发期可留空走 Vite 代理)。
- `fetch` + `ReadableStream.getReader()` + `TextDecoder`,按行切分,只消费 `data:` 前缀行,JSON.parse 后逐帧 yield。
- `AbortSignal` 透传,支持取消。
- `X-User-Id` 请求头传用户标识。

### 6.2 状态层 `stores/socratic.ts`

- 每次新生成先 `abort()` 上一个 `AbortController`——**流式请求必须可打断**,否则快速连点会并发脏数据。
- 流式过程中按 `section` 实时分类到 `questionsSection/assumptionsSection/reflectionSection`。
- 流结束后用正则从全文二次提取板块(`parseSections`),双保险。

### 6.3 代理配置(开发期二选一)

```ts
// vite.config.ts —— 走代理(前端代码仍用相对路径 /api/socratic)
server: { proxy: { '/api/socratic': { target: 'http://localhost:8001', changeOrigin: true } } }
```

或直连(代码里写死 `VITE_SOCRATIC_API_URL=http://localhost:8001`,依赖 CORS `*`)。

## 7. 如何复用:开发下一个"人格微服务"的步骤

这是本文档的**最终落点**。在项目里新开发一个 AI 对话组件时,按下面流程走。

### 7.1 三步走

```
Step 1  复制骨架
        ├─ 整体复制 苏格拉底对话/ 目录结构(main / core / api / services)
        ├─ 改服务名、端口(见 7.3 坑1),保留 spark_service.py 原样
        └─ requirements.txt 原样(已含全部依赖)

Step 2  换人格(唯一的核心开发量)
        ├─ 新增 services/<新人格>_prompt.py:
        │     SYSTEM_PROMPT = 新人格全文(角色 + 输出格式 + 边界 + 分级策略)
        │     build_user_prompt(...) = 新业务的用户消息拼装
        └─ api/ 下新增一个路由:
              端点命名对齐业务(如 /api/navigator/chat)
              事件名对齐目标前端契约(见 7.3 坑2)

Step 3  接线
        ├─ 后端: 从 stream_chat() 消费,按新事件名翻译后透传 SSE
        ├─ 前端: 复制 api/socratic.ts 模式(fetch + ReadableStream + AbortController)
        └─ 配 .env / vite proxy / 端口
```

### 7.2 新人格检查清单

| 项 | 检查点 |
|---|---|
| 人格层 | `SYSTEM_PROMPT` 是否含:角色定义/输出格式约束/边界禁忌/分级参数 |
| 引擎层 | `spark_service.py` 是否原样复用(未改动) |
| 密钥 | 是否只存在于 `.env`,未硬编码 |
| 流式 | 是否真流式(httpx.stream),无 `sleep()` 伪造 |
| 错误 | 是否全部转 SSE `error` 事件,不抛给路由 |
| 契约 | SSE 事件名是否与目标前端 `handleSSEEvent` 完全一致 |
| 取消 | 前端是否支持 AbortController 打断 |

### 7.3 常见坑(踩过)

| 坑 | 现象 | 对策 |
|---|---|---|
| **端口冲突** | 新服务用默认 8001,与项目后端 8001 撞 | 新服务必须换端口(如 8002),写入 `core/config.py` |
| **事件名错位** | 前端收不到/乱码 | 新人格的事件名以**目标前端已实现的 handler** 为准,先读前端 store 再定事件 |
| **思维链泄漏** | `reasoning_content` 被当成正文 | 前端无 thinking 通道时,在服务侧丢弃 reasoning 帧 |
| **密钥入库** | `.env` 忘加进 `.gitignore` | 首次提交前检查;`SPARK_API_PASSWORD` 永不明文入仓库 |
| **CORS 误配** | 直连模式跨域失败 | 开发期 `allow_origins=["*"]`;生产按需收口到前端域名 |

## 8. 扩展方向(本模板的演进空间)

| 方向 | 做法 | 与现状差异 |
|---|---|---|
| 多轮对话 | 请求体加 `messages` 数组,`messages[:-1]` 注入历史 | `stream_chat()` 签名扩展一个历史参数 |
| 工具调用(function-calling) | 星火 `tools` 参数,返回意图后回调项目后端 | 引擎层加一段工具分支 |
| 会话持久化 | 落 MySQL(符合本项目单存储决策) | 服务由无状态变有状态,慎做 |
| 人格仓库化 | 多个 prompt 文件 + 路由表,一个微服务承载多个人格 | `generate-simple` 已经隐含支持 |

## 附录 B:苏格拉底人格全文(SSOT)

来源:`services/socratic_prompt.py` 的 `SYSTEM_PROMPT`(v1.0)。

```text
你是苏格拉底式导师。你的任务不是回答问题，也不是和用户对话——而是针对用户的问题生成一份"引导反思"。

严格遵守以下输出格式，用三个明确的段落输出，不要输出任何其他内容：

【引导性问题】
针对用户的问题，提出2-4个层层递进的问题。这些问题应该：
- 从用户已知的基础概念出发，逐步推导到他在问的新概念
- 每个问题前用序号标注（① ② ③ ④）
- 使用生活类比降低门槛（大数据过程 → 日常场景比喻）
- 绝不在问题中给出答案，只提出问题
- 问题之间要有逻辑递进关系

【关键假设检验】
指出用户问题中可能隐含的1-2个未经检验的前提假设。揭示这些假设被检验后会怎样改变对问题的理解。使用简洁有力的语言，每条假设控制在40字以内。

【一句话反思】
用一句话（不超过40字）总结对这个问题最关键的认知洞察。这一句话应该让学生感到"原来如此"的顿悟感。

核心原则：
- 绝不直接回答知识性问题
- 不评价用户"你问得好"或"这很重要"
- 根据用户水平调整：初学者多用类比，进阶者多挑战假设
- 整个反思不超过300字
- 语言简洁，每句话都有信息量
```
